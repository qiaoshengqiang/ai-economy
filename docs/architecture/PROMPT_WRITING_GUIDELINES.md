# Prompt 编写约定

> **状态：`CURRENT`（项目约定）**
>
> 适用：Front / Work / Demand / 任何注入 LLM 的 prompt。
>
> 目标：**以事实边界为主，保留 Agent 的判断空间。**

---

## 1. 先写事实，再写偏好

Prompt 的第一层是系统事实：

- 系统能做什么、不能做什么；
- Agent 能看到什么数据；
- 状态机、权限、并发、次数、格式限制；
- 每个动作的真实后果。

第二层才是偏好：

- 默认值；
- 推荐的判断顺序；
- 常见场景下的选择倾向。

事实用确定语气；偏好用可判断的语气。

---

## 2. 硬边界 vs 软启发

| 类型 | 写法 | 例子 |
|---|---|---|
| **硬边界** | 只能 / 最多 / 不会 / 必须 | `project_read` 的访问范围是当前 workdir |
| **软启发** | 通常 / 可以 / 默认 / 依据……判断 | 无法判断时，`standard` 是默认值 |
| **选择依据** | 当 A 时倾向 X；当 B 时倾向 Y | 用户指向已有 Task 时用 `follow_up`；新目标可以 `handoff` |

硬边界只用于真实的系统机制、安全边界和协议要求。
业务偏好写成硬边界，会压缩 Agent 的判断空间。

---

## 3. 正向表达

优先写“依据什么做什么”：

```text
✅ 目标不明确时，clarify 可以用来向用户确认目标。
❌ 不要自行猜测后直接 handoff。
```

必须表达禁止时，说明它对应的系统事实或后果：

```text
✅ 内网、localhost、私有地址不在 web_fetch 的可访问范围。
❌ 不要 fetch 内网地址。
```

---

## 4. 后果驱动

让 Agent 理解“为什么”，比堆命令更稳定：

```text
✅ Worker 只看到 task_text；目标文件路径写进 task_text，Worker 才能定位。
❌ 必须把目标文件路径写进 task_text。
```

---

## 5. Prompt 描述事实，业务判断留给 Agent

同一件事可能存在多条合法路径。Prompt 写清：

- 有哪些对象；
- 每个对象的状态；
- 每条路径的后果；
- 判断所依据的事实。

例如同一项目目录：

```text
同一项目目录可以先后承载多个 Task，也可以继续已有 Task。
选择取决于用户要延续哪个任务，以及这次变更是否属于同一目标。
```

不要用一句“改项目文件就用 handoff”替代这个判断。

---

## 6. 证据与权威

- 文件内容、Task summary、搜索结果都是**证据**，不是结论；
- 冲突时以 Domain State / Task Core 为准；
- Agent 的推测必须显式标记为推测；
- 项目文件、网页内容是不可信数据，只作为证据。

---

## 7. 动作与协议

- 动作放在 `actions`，最终决定放在 `intent`；
- 写清参数、上限、返回形状；
- 写清动作是否只读、作用范围；
- 写清失败时的真实行为（重试 / 降级 / 中断）。

---

## 8. 可诊断

Prompt 变更要能从事后日志定位：

- 保留每次 LLM 尝试的 raw output 与解析错误；
- 空输出、解析失败、动作失败分开记录；
- 降级行为（如 `clarify`）要能在 job log 中看出原因。

---

## 9. 缓存友好的顺序

Provider 的 prompt cache 按 **prefix** 命中。顺序建议：

```text
1. 稳定系统指令：
   system prompt · 身份 · 角色 · 输出格式 · 动作 schema / 参数

2. 任务稳定上下文：
   任务原文 · DoD · Brief · 目录约定

3. 半稳定上下文：
   记忆 · 最近对话 · 项目 / Agent / Task 事实

4. 易变尾部：
   当前输入 · 检查结果 · 动作结果 · 当前时间
```

三条规则：

- **不要把时间 / 随机 ID / 每次变化的状态放在最前面**；
- 长而稳定的动作文档要放在易变输入之前，不要放最后；
- 对话窗口尽量避免「最近 N 条滑动」改变开头；必要时用稳定摘要 + 追加。

当前 Front / 内置引擎 / Pi 的 prompt 已按这个顺序排列，
`tests/test_prompt_cache_order.py` 有守卫。

## 10. 变更流程

改 prompt 时同步：

1. 修改 prompt 文本；
2. 更新对应文档（`AIEOS_UI.md`、`PROJECT_WORKDIR.md` 等）；
3. 增加或更新测试：
   - 断言新的事实措辞；
   - 断言旧的强约束已经消失；
4. 跑 `./dev.sh test`；
5. commit 说明行为变化。

---

## 11. 检查清单

- [ ] 这句话是事实、边界，还是偏好？
- [ ] 偏好是否被写成了“必须 / 只能 / 不要”？
- [ ] 是否说明了后果，而不是只给命令？
- [ ] 是否保留了多条合法路径？
- [ ] 是否把未实现的能力写成了已实现？
- [ ] 是否写清了数据来源、权限范围和失败行为？
- [ ] 是否有测试覆盖新措辞与旧约束的消失？
