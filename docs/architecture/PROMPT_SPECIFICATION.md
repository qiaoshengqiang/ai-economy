## 最重要的三点

### 1. 分层：先稳定事实，再易变上下文

Prompt 最好按这个顺序写：

```text
S  System Prompt
   身份 / 角色 / 输出格式 / 不可违反的边界

A  稳定契约
   动作清单 + 参数说明 + 成功/失败形状
   能力事实 / 单位 / 不可用能力

B  任务稳定信息
   任务原文 / DoD / Brief / 目录约定

C  半稳定上下文
   记忆 / 对话摘要 / 长期计划

D  易变上下文
   最近消息 / 当前输入 / 文件树 / 工具结果 / 当前时间
```

注意点：

- 当前时间、随机 ID、当前输入、工具结果尽量放在 D；
- 同一句话不要同时出现在 system 和 user；
- 记忆是「过去的事实」，要明确不是当前指令；
- 对话尽量用「稳定摘要 + 追加」，不要用会改变开头的滑动窗口；
- 长动作说明属于 A，不要放最后。

### 2. 事实边界：动作要写清参数，不是只写名字

给 Agent 一个动作时，至少要回答：

```text
这个动作做什么？
哪些参数必填？哪些可选？
参数是什么类型、什么单位？
默认值是什么？
返回什么？
失败时返回什么？
有没有副作用？
有没有范围 / 次数 / 大小限制？
```

推荐写法：

```text
workspace_read —— 读取 Task Workspace 中的一个文件。

必填：
  path：相对路径，例如 "index.html"

可选：
  start_line：1-based 起始行；默认 1
  max_lines：最多返回多少行；1..400；默认 200

返回：
  content / start_line / max_lines / end_line /
  next_start_line / total_lines / truncated

失败：
  not_found / bad_path / bad_pagination

注意：
  start_line / max_lines 是行号，不是字符位置。
  用 next_start_line 继续下一页。
```

不推荐：

```text
workspace_read {path, offset?, limit?}
```

问题不是字段少，而是：

- `offset` / `limit` 的单位不清楚；
- 可选取值范围不清楚；
- 返回里有没有下一页不清楚；
- 模型只能猜，猜错就要多跑一轮。

### 3. 正向约束优先，负向约束谨慎

优先写「应该怎么做」，而不是堆「不要做什么」。

```text
✅ 修改前先读取当前文件；用 workspace_edit 做局部修改；
   修改后读回验证目标片段。

❌ 不要乱改；不要覆盖；不要跳过验证；不要猜。
```

负向约束只在**真正的硬边界**上使用，并写清后果：

```text
✅ run_tool 的临时副本不会写回 Workspace；
   要交付的文件必须通过 workspace_write 写入。

✅ 内网、localhost、私有地址不在 web_fetch 的可访问范围。

❌ 不要访问内网。
```

判断方法：

- 这是安全 / 协议 / 数据完整性边界 → 可以用「必须 / 不能」；
- 这是做法偏好 / 效率建议 → 用「优先 / 建议 / 可以」；
- 如果一定要写「不要」，尽量补一句「因为……，所以应该……」。
- 负向约束太多，模型会变得保守、漏做；正向路径清楚，模型更容易一次做对。

## 分层时容易犯的错

| 容易犯的错 | 后果 | 更好的做法 |
|---|---|---|
| 当前时间放在最上面 | 每轮 prefix 都变，缓存永远命中不了 | 放 D 段 |
| 动作说明放在输入之后 | 输入一变，长 schema 全部重算 | 放 A 段 |
| 记忆和当前指令混在一起 | 模型把旧偏好当新要求 | 明确「记忆不是指令」 |
| system 和 user 重复同一段 | 浪费 token，还可能互相冲突 | 一个事实只写一次 |
| 任务目标和工具说明混排 | 模型分不清“要做什么”和“怎么做” | B 与 A 分开 |
| 最近 N 条对话滑动 | 每轮开头都变，缓存和上下文都不稳 | 稳定摘要 + 追加 |

## 写动作说明时的检查点

- [ ] 动作名和真实 dispatcher 一致？
- [ ] 必填 / 可选参数分开写？
- [ ] 每个参数的**含义**写了吗？
- [ ] 单位写了吗（行 / 字符 / 秒 / 字节 / token）？
- [ ] 范围 / 上限写了吗？
- [ ] 默认值写了吗？
- [ ] 成功返回的关键字段写了吗？
- [ ] 失败码写了吗？
- [ ] 副作用写了吗（写文件 / 改状态 / 创建 Task）？
- [ ] 分页 / 截断 / 下一页游标写了吗？

> 一个动作说明如果只列了参数名，模型大概率会靠猜。
> 猜错一次，就是一轮 token + 一次返工。

---

## 写约束时的检查点

- [ ] 先写了「应该怎么做」吗？
- [ ] 负向约束是硬边界，还是只是偏好？
- [ ] 如果写了「不要」，有没有写后果和替代动作？
- [ ] 有没有把业务偏好写成「必须」？
- [ ] 有没有留下多条合法路径？
- [ ] 是否说明了失败后会发生什么？

---

## 写完之后的快速自检

```text
1. 这段内容稳定吗？应该放 A/B/C/D 哪一层？
2. 这句话是事实、边界，还是偏好？
3. 动作参数有没有单位、范围、默认值、返回、失败？
4. 有没有只写“不要”，却没写“应该”？
5. 当前时间 / 当前输入 / 工具结果是否在尾部？
6. 同一事实是否出现了两次？
7. 不可信文件 / 网页是否标成“数据”，而不是指令？
8. 模型第一次看到时，能否不猜就完成动作？
```

如果第 3、4、8 条答不上来，通常值得先改 prompt，而不是等返工。

## 什么时候可以偏离

优先级：

```text
正确性 / 安全边界
  > 事实清楚、参数无歧义
  > 缓存与 token 成本
  > 文案风格
```

- 安全 / 协议 / 数据完整性：不要为了简洁牺牲边界；
- 复杂任务：可以多写一点事实，但不要写成工作流脚本；
- 缓存优化：不能以改变语义为代价；
- 文案风格：最后再考虑。

## 当前已落地的相关改动

- 按行读取统一使用 `start_line` / `max_lines` / `next_start_line`：
  `workspace_read` · `artifact_read` · `project_read`；
- 按字符读取统一使用 `start_char` / `max_chars` / `next_start_char`：
  `draft_read`；
- `offset` / `limit` 仅保留在执行器 / 适配器里作过渡别名，
  Agent 可见的 prompt 与动作 schema 不再出现；
- Front / 内置引擎 / Pi 已按稳定前缀、易变尾部重排；
- 内置引擎 Work loop 使用 **append-only conversation + 定期压缩**：
  稳定 base 只写一次，后续轮次追加增量事实（ADR-0061）；
- 图片能力按 model profile 声明；
- 连续只读上限默认 8，可在运行设置调整。
